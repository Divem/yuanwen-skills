## 我们要解决什么

<!-- 适用条件：中型及以上项目必选；小项目可省 -->

LLM 写代码有几个典型陷阱：

- **臆测前提**：不假思索按错误假设执行，不主动澄清矛盾、不展示权衡
- **过度复杂**：堆抽象、堆配置、堆 fallback、不清理死代码
- **越界编辑**：动了与任务无关的代码、注释、格式
- **目标模糊**：不写"完成判据"就开工，靠手感判断对不对

下面 4 条原则正面回应这些陷阱。**红线规则**则是项目自身不能踩的硬约束。

## 原则详解

### 1. 编码前思考
> **不要臆测。不要藏起困惑。把权衡摊出来。**

- 说清假设；遇到歧义时列出解读并请用户选择，不要默默猜测
- 需求不清就停下来问，不要自行补充需求
- 看到代码与意图矛盾，先核对事实并指出差异，不要绕过

**检验标准：** 干完之后，用户是否会问"你为什么没问我 X？"

### 2. 简洁优先
> **能 50 行就别写 200 行。不为不可能的输入兜底。**

- 不增加任务之外的功能、配置或抽象；重复 3 次再考虑抽象
- 不可填的值用空值类型（`None` / `null`），不要兜底成空字符串或 `-1`
- 不保留“将来可能用”的 unused 接口；只在用户输入、外部 API 等系统边界做必要校验

**检验标准：** 资深工程师 review 时，会觉得这段实现"过度设计"吗？

### 3. 精准修改
> **只动用户要的那行。只清自己造的烂摊子。**

- 不顺手改进相邻代码、注释或格式，也不重构能正常工作的代码；重构应单独立项
- 匹配现有风格，不要按个人偏好改命名/结构
- 无关死代码只标注、不删除；仅清理本次改动产生的 unused 内容

**检验标准：** `git diff` 每一行都能追溯到本次任务吗？

### 4. 目标驱动
> **先写完成判据，再开工。验证到通过为止。**

- 把“加校验”“修 bug”“重构”等模糊指令改写为可执行测试或复现步骤
- UI 工作明确组件、屏宽和截图或浏览器验收标准
- 多步骤任务先写“步骤 → 验证”，再逐项完成

**检验标准：** 在动手前，能不能用一句话写出"完成的样子"？
