## 六层心智模型

一份高质量 AGENTS.md 分六层，从抽象到具体：

| 层 | 章节 | 通用 / 项目特定 | 回答什么 |
|---|---|---|---|
| **元信息** | 标题 + 定位 | 项目特定 | 这是什么项目？技术栈？ |
| **动机** | 我们要解决什么 | 半通用 | 为什么要这些规则？ |
| **通用原则** | 编码原则总览 + 详解 + 反例 | 通用（跨项目） | 怎么写代码才对？ |
| **项目红线** | 红线规则 | 项目特定 | 哪些事绝对不能做？ |
| **操作知识** | 命令 / Gotchas / 自检 / 提交 / 文档 | 项目特定 | 具体怎么操作？踩过什么坑？ |
| **参考** | 关键参考 | 项目特定 | 去哪查更多？ |

**核心洞察**：通用原则层（编码前思考 / 简洁优先 / 精准修改 / 目标驱动）几乎跨所有项目通用，应保持稳定；项目特定层（红线、Gotchas、命令）随项目演化，是真正需要持续维护的部分。诊断时优先查项目特定层是否过时。

## 1. 标题与一句话定位

**用途**：让 agent 在第一秒就知道这是什么项目、用什么技术栈、解决什么问题。

**写法**：标题 `# AGENTS.md` + 一段引用块，包含三要素——项目名、一句话定位、技术栈。

✅ 好示例：
```markdown
# AGENTS.md

> **Coder Friends**：本地优先的 AI 编程助手管理桌面客户端。Tauri 2.0 + React 19 + Rust + SQLite。
```

❌ 坏示例（只有标题，或缺技术栈）：
```markdown
# AGENTS.md
本文件描述项目规则。
```

**诊断信号**：开头没有技术栈、没有一句话定位 → agent 缺乏项目全貌，容易做错技术选型假设。

## 2. 我们要解决什么（动机层）

**用途**：把"规则"和"痛点"绑定。没有动机的规则是教条，agent 记不住也不会主动应用。

**写法**：先列 LLM 写代码的典型陷阱（项目实际遇到过的优先），再说明下面的原则如何正面回应这些陷阱。

✅ 好示例：
```markdown
LLM 写代码有几个典型陷阱：
- **臆测前提**：不假思索按错误假设执行
- **过度复杂**：堆抽象、堆配置、堆 fallback
- **越界编辑**：动了与任务无关的代码
- **目标模糊**：不写"完成判据"就开工
```

❌ 坏示例（直接堆规则，不解释为什么）：
```markdown
## 编码规范
1. 编码前要思考
2. 代码要简洁
3. 不要改无关代码
```

**诊断信号**：规则堆砌但无动机 → 标记"动机缺失"，建议补痛点说明。这是 AGENTS.md 最常见的缺陷。

## 3. 编码原则总览

**用途**：用一张表让 agent 30 秒抓住全部原则及其针对的痛点。

**写法**：表格两列——原则名 / 解决什么。原则数量控制在 3–5 条（coder-friends 是 4 条）。

✅ 好示例：
```markdown
| 原则 | 解决什么 |
|---|---|
| **编码前思考** | 错误假设、隐藏歧义、缺少权衡 |
| **简洁优先** | 过度抽象、未来主义、复杂兜底 |
| **精准修改** | 越界编辑、顺手重构、删不该删 |
| **目标驱动** | 没有验证标准，自我感觉良好 |
```

**诊断信号**：原则多于 6 条（记不住）或少于 3 条（覆盖不够）、或原则与痛点未对齐。

## 4. 红线规则（项目硬约束）

**用途**：列出项目自身**违反必返工**的硬约束。这是 AGENTS.md 区别于通用编码指南的核心价值——只有这个项目的 agent 需要知道的东西。

**写法**：每条规则要**具体、可执行、有触发条件和后果**，而非口号。

✅ 好示例（具体可执行）：
```markdown
1. **8 个 sync adapter 一致性**：改 `src-tauri/src/main/sync/`、`tool_id` 后，必须确认 8 个 adapter 仍能编译。改完 trait 立刻跑 `cargo check`。
2. **不主动 push / tag**：未经用户明确指示，禁止 `git push`、`git tag`。
3. **i18n 不硬编码**：用户可见文案走 `locales/en.json` + `zh.json`。组件内禁止中/英文字面量。
```

❌ 坏示例（口号化，不可执行）：
```markdown
1. 注意代码质量
2. 保证一致性
3. 做好国际化
```

**红线规则的典型来源**（诊断时帮项目找）：
- **一致性约束**：多处需同步修改的地方（adapter / registry / migration / 路由）
- **工作流约束**：强制流程（OpenSpec propose→apply→archive、改动前先 propose）
- **安全约束**：不主动 push / tag / 部署、不提交密钥、不提交构建产物
- **硬编码禁令**：i18n key、tool_id、magic number、配置项不能写死字面量

**诊断信号**：红线写成口号、或把通用原则当红线、或缺少"触发→后果"结构。

## 5. 原则详解 + 检验标准

**用途**：把总览里的每条原则展开，给出可执行的子规则和**检验标准**。检验标准是灵魂——它让"是否遵守原则"可被客观判断。

**写法**：每条原则 = 一句格言式核心（引用块）+ 子规则 bullet + `**检验标准：**` 一句话（以"用户是否会…"或"能不能…"开头）。

✅ 好示例：
```markdown
### 2. 简洁优先
> **能 50 行就别写 200 行。不为不可能的输入兜底。**

- 不加任务之外的功能、抽象、配置项
- 不为单次脚本设计 trait；重复 3 次再抽象
- `Option<T>` 不可填时用 `None`，不要兜底成空字符串或 `-1`

**检验标准：** 资深工程师 review 时，会觉得这段实现"过度设计"吗？
```

❌ 坏示例（无检验标准，原则无法验证）：
```markdown
### 简洁优先
写代码要简洁，不要过度设计。
```

**诊断信号**：原则详解无"检验标准" → 标记为高优先级修复。这是判断 AGENTS.md 质量的关键指标。

---

## 6. 反例对照表

**用途**：用"❌ 不该做 / ✅ 应该做"对照表，把抽象原则落到具体代码场景。比文字描述更易被 agent 应用。

**写法**：两列表格，左列写真实踩过的坑（带代码片段），右列写正确做法。

✅ 好示例：
```markdown
| ❌ 不该做 | ✅ 应该做 |
|---|---|
| `Option<T>` 兜底用空字符串 / `-1` | 严格 `None`，调用方显式处理 |
| 在组件里 `if tool_id === "claude-code"` | 走 `TOOL_REGISTRY` 或策略对象 |
| 改 Rust trait 后才发现编译失败 | 改完立即 `cargo check` |
```

**诊断信号**：有原则详解但无反例对照 → 原则停留在口号层，agent 难以落地。

---

## 7. 命令速查

**用途**：让 agent 知道项目里每个常用操作的正确命令，避免臆测命令。

**写法**：代码块列出**实际可跑**的命令 + 注释说明用途。**必须注明项目没有的脚本**（如"无独立 typecheck 脚本，用 `npx tsc --noEmit`"）。

✅ 好示例：
```markdown
npx tsc --noEmit                                     # 类型检查（项目无独立 typecheck 脚本）
cargo check --manifest-path src-tauri/Cargo.toml     # Rust 快速验证
npm run i18n:sync-locales                            # 校验 locale key 一致
```

**诊断信号**：命令不能跑（已被删除/改名）、缺少关键命令（lint / typecheck / test / build / dev）、或列了不存在的脚本。**诊断时务必实际验证命令是否存在**——查 `package.json` 的 `scripts`、`Makefile`、`Cargo.toml` 等。

## 8. 架构 Gotchas

**用途**：沉淀项目里"看起来显而易见、实际容易踩坑"的知识。这是 AGENTS.md 里**信息密度最高**、最难从代码本身推断的部分。

**写法**：每条 = 一个**反直觉事实** + 具体路径/键名。只写"不看就会错"的东西。

✅ 好示例：
```markdown
- **路径别名**：`@/` → `src/ui/`（**不是** `src/`）。
- **深色模式默认**：加载时 `document.documentElement.classList.add("dark")`。
- **数据库迁移**：新 schema 改动必须在 `migrations.rs` 加一条 migration。
- **Tauri 命令注册**：新 Rust command 要同时在 `commands/mod.rs` 和 `lib.rs` 注册。
```

❌ 坏示例（写显而易见的东西，浪费 context）：
```markdown
- 项目用 TypeScript
- 用 React 写组件
- 数据存在数据库里
```

**诊断信号**：Gotchas 写显而易见的事（信息量低），或缺失（agent 反复踩同样的坑）。诊断时主动问：项目里哪些约定不看就会错？

## 9. 提交前自检清单

**用途**：把"改动类型 → 必跑的验证"固化成 checklist，防止 agent 漏验证。

**写法**：每个 checkbox = 一个**可执行**的检查命令，附条件（"如改了 Rust"）。

✅ 好示例：
```markdown
- [ ] `npx tsc --noEmit` — 0 错误
- [ ] `cargo check` — 0 错误（如改了 Rust）
- [ ] 新增 i18n key 已加到 `en.json` + `zh.json`（如改了文案）
- [ ] DB 迁移加在 `migrations.rs`（如改了 schema）
- [ ] `git diff` 每行都能追溯到当前任务
```

❌ 坏示例（不可执行的口号）：
```markdown
- [ ] 代码没有 bug
- [ ] 测试通过
- [ ] 文档更新
```

**诊断信号**：自检项不可执行（无法判断是否完成）、或与红线规则/命令速查脱节。

---

## 10. 提交规范

**用途**：约束 commit message 格式，保证历史可追溯。

**写法**：指定规范（Conventional Commits 最常见）+ 正文要求（改了什么、为什么、影响范围、bug fix 写根因）。

✅ 好示例：
```markdown
Conventional Commits（`feat` / `fix` / `refactor` / `chore`）。
正文写**改了什么、为什么改、影响范围**。bug fix 要写明根因。
```

**诊断信号**：无提交规范、或规范与实际 git 历史不符。

---

## 11. 文档要求

**用途**：约束项目内文档的归属、命名、交叉引用，防止文档腐烂。

**写法**：指明文档目录结构、命名规则、何时产出、是否需互相引用。大型项目才有必要；小项目可省。

✅ 好示例：
```markdown
1. **技术设计** 放 `docs/tech/`，文件名 `-design` 后缀。
2. **PRD** 放 `docs/prd/`。
两份文档必须互相引用。新增/删除文档后更新对应目录的 `README.md`。
```

**诊断信号**：大项目无文档规范（文档必然乱）、或小项目堆了过度复杂的文档规范。

---

## 12. 关键参考

**用途**：把 agent 该读但不宜塞进 AGENTS.md 的深度文档，用链接索引出来。保持 AGENTS.md 精简。

**写法**：相对路径链接 + 一句话说明每份文档的作用。

✅ 好示例：
```markdown
- `docs/tech/database-schema.md` — 数据库 schema
- `docs/tech/new-tool-integration-guide.md` — 新增工具适配器流程
- `openspec/changes/` — 进行中与已归档的变更提案
```

**诊断信号**：链接指向不存在的文件、或缺少"必读踩坑文档"的索引。诊断时实际检查文件是否存在。

## 章节取舍决策表

不是所有项目都需要全部章节。按下表取舍：

| 章节 | 小项目（脚本 / 单文件） | 中型项目 | 大型项目 / 团队 |
|---|---|---|---|
| 标题 + 定位 | ✅ 必选 | ✅ 必选 | ✅ 必选 |
| 我们要解决什么 | ⚪ 可选 | ✅ 推荐加 | ✅ 必选 |
| 编码原则总览 | ⚪ 可选 | ✅ 必选 | ✅ 必选 |
| 红线规则 | ⚪ 看情况 | ✅ 必选 | ✅ 必选 |
| 原则详解 + 检验标准 | ⚪ 可选 | ✅ 必选 | ✅ 必选 |
| 反例对照表 | ❌ 跳过 | ⚪ 推荐加 | ✅ 必选 |
| 命令速查 | ✅ 必选 | ✅ 必选 | ✅ 必选 |
| 架构 Gotchas | ⚪ 看复杂度 | ✅ 必选 | ✅ 必选 |
| 提交前自检清单 | ⚪ 可选 | ✅ 推荐加 | ✅ 必选 |
| 提交规范 | ⚪ 可选 | ✅ 必选 | ✅ 必选 |
| 文档要求 | ❌ 跳过 | ⚪ 看情况 | ✅ 必选 |
| 关键参考 | ⚪ 可选 | ✅ 推荐加 | ✅ 必选 |

**总长度建议**：小项目 50–100 行；中型 150–250 行；大型 250–400 行。**超过 400 行考虑拆分到 `docs/` 并用"关键参考"索引**——AGENTS.md 太长反而降低 agent 遵守率。
