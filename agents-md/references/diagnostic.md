# AGENTS.md 诊断手册

> 诊断老项目 AGENTS.md 时按本手册执行。核心原则：**不只读文本，必须实际验证**——命令要跑、文件要查、链接要确认存在。文本看起来齐全但实际失效，是 AGENTS.md 最危险的腐烂方式。

## 诊断流程

```
1. 读完整份 AGENTS.md（及 CLAUDE.md，确认引用关系）
2. 通览项目结构，识别项目类型与规模
3. 逐维度执行 11 维度检查（每条都实际验证，不臆测）
4. 汇总发现，按严重度分级
5. 输出结构化诊断报告 + 可执行的优化建议
```

**验证类工具调用（务必跑，不要只看）**：
- 查命令是否存在：`cat package.json | jq .scripts` / 读 `Makefile` / 读 `Cargo.toml` 的 `[workspace]`
- 查文件是否存在：`ls docs/tech/*.md` / `test -f path && echo ok`
- 查命令能否跑：`npx tsc --noEmit --version` 等轻量验证（不要跑完整构建，太慢）
- 查 git 历史规范：`git log --oneline -20` 看实际 commit 风格
- 查 CLAUDE.md 与 AGENTS.md 是否重复：diff 两份文件，找出复制粘贴的部分
- 查 AGENTS.md 内部重复：对照动机、原则详解、反例、红线和自检，识别同义复述
- 查易腐烂快照：搜索 `截至|目前|当前|YYYY-MM-DD|测试.*个|错误.*个`，判断是否应改为稳定规则

## 11 维度检查矩阵

### 维度 1：动机层（Why）

| 检查点 | 信号 | 严重度 |
|---|---|---|
| 是否有"我们要解决什么 / 为什么这些规则"章节 | 规则堆砌无动机 | 🔴 高 |
| 痛点是否真实、是否与原则对齐 | 痛点空泛或与原则脱节 | 🟡 中 |

**修复手法**：补一段动机说明，列 LLM 在**本项目**实际踩过的坑，把每条原则绑定到一个痛点。

---

### 维度 2：编码原则完整性与检验标准

| 检查点 | 信号 | 严重度 |
|---|---|---|
| 是否有 3–5 条编码原则总览 | 缺失 / 过多（>6）/ 过少（<3） | 🔴 高 |
| **每条原则是否有"检验标准"** | 原则不可验证 | 🔴 高 |
| 检验标准是否可客观判断（"用户是否会…" / "能不能…"） | 标准模糊 | 🟡 中 |

**修复手法**：为每条原则补一句 `**检验标准：** …`。参考 `principles.md` 的标准写法。这是提升 AGENTS.md 质量性价比最高的改动。

---

### 维度 3：红线规则质量

| 检查点 | 信号 | 严重度 |
|---|---|---|
| 是否有项目特定的红线规则 | 无红线 / 把通用原则当红线 | 🔴 高 |
| 红线是否具体可执行（触发条件 + 后果） | 口号化（"注意质量""保证一致"） | 🔴 高 |
| 红线是否覆盖四类来源（一致性 / 工作流 / 安全 / 硬编码） | 遗漏关键类别 | 🟡 中 |

**修复手法**：逐条红线改写为"触发条件 → 必做动作"。参考 `anatomy.md` 第 4 节的红线来源清单，主动帮项目找遗漏的红线（问：哪些改动需要多处同步？哪些操作不能 agent 自主做？哪些值不能写死？）。

---

### 维度 4：命令速查准确性

| 检查点 | 信号 | 严重度 |
|---|---|---|
| 命令是否真实可跑 | 命令已删除 / 改名 / 路径错 | 🔴 高 |
| 是否覆盖关键命令（dev / build / test / lint / typecheck） | 缺关键命令 | 🟡 中 |
| 是否注明"项目没有的脚本"及替代方案 | agent 臆测不存在的命令 | 🟡 中 |

**修复手法**：对照 `package.json` / `Makefile` / `Cargo.toml` 逐一核对。删掉不存在的命令，补上实际可用的，注明替代方案（如"无 typecheck 脚本，用 `npx tsc --noEmit`"）。

---

### 维度 5：架构 Gotchas 信息密度

| 检查点 | 信号 | 严重度 |
|---|---|---|
| Gotchas 是否为"不看就会错"的反直觉知识 | 写显而易见的事 | 🟡 中 |
| 是否覆盖项目已知踩坑点 | 缺关键 gotcha（agent 反复踩坑） | 🔴 高 |
| 是否包含具体路径 / 键名 / 文件名 | 笼统无定位 | 🟡 中 |

**修复手法**：删掉"显而易见"的条目（如"项目用 TypeScript"）。问项目维护者或查 git 历史/issue，补上真实的踩坑点。每条 gotcha 必须带具体路径。

---

### 维度 6：提交前自检清单可执行性

| 检查点 | 信号 | 严重度 |
|---|---|---|
| 每个 checkbox 是否可执行（有命令或明确动作） | 口号化（"代码无 bug"） | 🔴 高 |
| 是否覆盖红线规则要求的验证 | 红线无对应自检项 | 🟡 中 |
| 是否与改动类型挂钩（"如改了 X"） | 无条件罗列全部检查 | 🟢 低 |

**修复手法**：把每个不可执行的 checkbox 改写为具体命令，附条件标注。确保每条红线规则都能在自检清单里找到对应的验证项。

---

### 维度 7：CLAUDE.md 与 AGENTS.md 关系

| 检查点 | 信号 | 严重度 |
|---|---|---|
| 是否遵循单一规则源（CLAUDE.md 用 `@AGENTS.md` 引用） | 两份文件大量重复 | 🟡 中 |
| CLAUDE.md 是否默认仅引用 `@AGENTS.md` | 复制通用规则或无必要的命令清单 | 🟡 中 |
| 其他 agent（Codex 等）能否只读 AGENTS.md 就够 | 通用规则只在 CLAUDE.md | 🟡 中 |

**修复手法**：将通用规则迁移到 AGENTS.md，CLAUDE.md 默认只保留 `@AGENTS.md`。仅在用户明确需要、且内容无法由共享规则表达时追加经核实的 Claude 特化项。其他入口文件也优先收敛为薄引用。

---

### 维度 8：篇幅与结构

| 检查点 | 信号 | 严重度 |
|---|---|---|
| 总长度是否在合理区间（小 50–100 / 中 150–250 / 大 250–400 行） | 过长（agent 遵守率下降）或过短（信息不足） | 🟡 中 |
| 是否有清晰的层级标题便于导航 | 一坨平铺文本 | 🟡 中 |
| 是否有过时信息（删掉的文件、改名的模块、废弃的流程） | 文档腐烂 | 🔴 高 |

**修复手法**：过长的内容拆到 `docs/` 并用“关键参考”索引。逐条核对提到的路径/模块名是否仍存在。行数落在建议区间内不代表足够紧凑，继续执行维度 9。

---

### 维度 9：精简度与信息密度

| 检查点 | 信号 | 严重度 |
|---|---|---|
| 动机、原则、反例、红线、自检是否同义重复 | 同一规则换措辞出现 2–3 次 | 🟡 中 |
| 是否包含日期、测试数量、当前错误数等运行快照 | 内容短期内必然失效，却没有维护来源 | 🟡 中 |
| 每段是否会改变 agent 行为 | 删除后不影响决策或验证方式 | 🟢 低 |
| 通用说明与项目知识比例是否合理 | 通用教程挤占项目红线和 Gotchas | 🟡 中 |
| 详细 SOP 是否应下沉到 docs | AGENTS.md 复制整份文档规范或流程手册 | 🟡 中 |

**修复手法**：保留原则名、检验标准、项目红线和项目特定反例；删除同义复述。把“截至某日有 N 个测试 / M 个错误”改成“运行命令并区分既有与新增失败”。长 SOP 下沉到 `docs/`，入口只写触发条件与链接。

**行为变化测试**：逐段问“删掉这段后，agent 的决策、操作或验证会改变吗？”不会则删除、合并或下沉。

---

### 维度 10：文档要求适配度

| 检查点 | 信号 | 严重度 |
|---|---|---|
| 大项目是否有文档规范 | 大项目无文档规范 → 文档必然乱 | 🟡 中 |
| 小项目是否堆了过度文档规范 | 小项目文档规范比代码还重 | 🟢 低 |
| 文档规范是否与实际 docs/ 结构一致 | 规范说的目录不存在 | 🟡 中 |

**修复手法**：按项目规模调整。参考 `anatomy.md` 章节取舍决策表。

---

### 维度 11：可维护性

| 检查点 | 信号 | 严重度 |
|---|---|---|
| 是否有版本/更新提示 | 无维护机制，写完即腐烂 | 🟢 低 |
| 规则是否有自我引用（指向文档、issue、决策记录） | 规则无溯源 | 🟢 低 |
| 是否区分"通用稳定层"与"项目易变层" | 全混在一起，改一处要全文审 | 🟡 中 |

**修复手法**：明确分层（通用原则层稳定、项目特定层随演化）。给易变规则加文档链接溯源。

## 严重度分级

- 🔴 **高（致命）**：直接导致 agent 行为错误或规则失效。如命令不能跑、红线口号化、原则无检验标准、文档腐烂。**必须修复**。
- 🟡 **中（重要）**：降低 AGENTS.md 有效性但不致命。如缺动机层、Gotchas 信息密度低、两份文件重复。**建议修复**。
- 🟢 **低（优化）**：锦上添花。如可维护性提示、条件标注。**可选**。

## 常见病症库

### 病症 A：规则教条化（最常见）

**症状**：通篇"要简洁""要测试""注意质量"，无 Why、无检验标准、无反例。

**处方**：
1. 补"我们要解决什么"动机层
2. 每条原则补 `**检验标准：**`
3. 加反例对照表（❌ / ✅）

### 病症 B：通用原则与项目知识混在一起

**症状**：把"不主动 push"（通用）和"8 个 adapter 一致性"（项目特定）平铺，无分层。

**处方**：拆成"编码原则（通用稳定）"和"红线规则（项目特定）"两层。参考 `principles.md` 的通用原则全集。

### 病症 C：文档腐烂

**症状**：提到 `src/legacy/` 但该目录早已删除；命令引用 `npm run lint` 但 scripts 里没有。

**处方**：逐条核对路径与命令实际存在性。建立"每季度 review 一次 AGENTS.md"的提示。

### 病症 D：CLAUDE.md / AGENTS.md 复制粘贴

**症状**：两份文件 80% 内容相同，改一处忘改另一处。

**处方**：CLAUDE.md 默认只留 `@AGENTS.md`；仅在确有必要时追加最少的 Claude 特化项。单一规则源。

### 病症 E：过载（AGENTS.md 当 README 用）

**症状**：400+ 行，混入大量项目介绍、安装说明、API 文档。agent 读不完、遵守率低。

**处方**：把深度内容迁到 `docs/`，AGENTS.md 只留规则 + 索引。

### 病症 F：口号化红线

**症状**：红线写成"保证数据安全""做好错误处理"，不可执行。

**处方**：每条红线改写为"触发条件 → 必做动作"。参考 `anatomy.md` 第 4 节。

### 病症 G：行数合规但内容松散

**症状**：总行数在建议范围内，但原则详解与反例重复，或记录“截至某日有 N 个测试 / M 个错误”等快照。

**处方**：执行维度 9 的行为变化测试；只保留项目特定反例，把运行快照改成稳定验证规则或迁移到报告。

## 诊断报告输出格式

诊断完成后，按以下结构输出报告（给用户看）：

```markdown
# AGENTS.md 诊断报告

## 总览
- 项目类型：[小/中/大型] / [技术栈]
- 当前篇幅：[行数] | 建议区间：[区间]
- 精简度：[紧凑 / 有少量重复 / 明显松散] | 时效快照：[无 / N 处]
- 健康度评分：[A+/A/B/C/D]（基于高/中/低问题数量）

## 🔴 致命问题（必须修复）
1. [问题] — [具体位置] — [修复建议]
2. ...

## 🟡 重要问题（建议修复）
1. ...

## 🟢 优化项（可选）
1. ...

## 亮点（做得好的地方）
- [具体表扬，让用户知道哪些不用动]

## 修复优先级建议
1. 先修 [最高优先级] —— 因为 ...
2. 再修 ...
```

**报告原则**：
- 每个问题必须给**具体位置**（章节名 / 行号）和**可执行修复建议**，不要泛泛而谈
- 必须有"亮点"段落——告诉用户哪些不用动，避免过度修改
- 修复建议尽量给可直接套用的改写示例

## 优化优先级排序

当问题很多时，按此顺序修（性价比从高到低）：

1. **删事实腐烂**：删掉失效命令、不存在的路径 → 零成本，消除误导
2. **删时效快照和内部重复**：稳定规则替代日期/数量，项目反例替代通用复述 → 降低维护成本
3. **补检验标准**：给每条原则补 `**检验标准：**` → 一句话，质量提升巨大
4. **红线具体化**：口号红线改写为"触发→动作" → 防止致命违规
5. **收敛规则源**：CLAUDE.md 默认只保留 `@AGENTS.md` → 消除维护负担
6. **补动机层**：加"我们要解决什么" → 让规则可被理解和主动应用
7. **补项目反例**：用真实代码场景替代通用教程 → 提升信息密度
8. **补架构 Gotchas**：沉淀踩坑知识 → 防止重复踩坑
9. **拆分过载内容**：长内容迁 docs/ → 提升遵守率
