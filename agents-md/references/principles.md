## 4 条通用编码原则（默认采用）

这 4 条正面回应 LLM 写代码的 4 个典型陷阱，**建议所有项目原样采用**：

| 原则 | 解决什么 | 是否通用 |
|---|---|---|
| **编码前思考** | 臆测前提、隐藏歧义、缺少权衡 | ✅ 全通用 |
| **简洁优先** | 过度抽象、未来主义、复杂兜底 | ✅ 全通用 |
| **精准修改** | 越界编辑、顺手重构、删不该删 | ✅ 全通用 |
| **目标驱动** | 没有验证标准，自我感觉良好 | ✅ 全通用 |

下面是每条的**可直接复制**全文（含格言、子规则、检验标准）。

---

## 原则 1：编码前思考

> **不要臆测。不要藏起困惑。把权衡摊出来。**

- 假设说清楚——不确定就问，不要"猜一下试试"
- 歧义场景列出多种解读，请用户选，不要默默选一个
- 看到代码与意图矛盾，提出来，不要绕过
- 需求不清就停下来问，不要默默补需求

**检验标准：** 干完之后，用户是否会问"你为什么没问我 X？"

**适配提示**：如项目用 spec 驱动流程（如 OpenSpec），在子规则里点明"需求不清先 propose 而非默默补"。

---

## 原则 2：简洁优先

> **能 50 行就别写 200 行。不为不可能的输入兜底。**

- 不加任务之外的功能、抽象、配置项
- 不为单次脚本设计抽象；重复 3 次再抽象
- 不可填的值用空值类型（`None` / `null` / `undefined`），不要兜底成空字符串或 `-1`
- 不为"将来可能扩展"留 unused 接口
- 不在内部代码里做防御性参数校验——只在系统边界（用户输入、外部 API）校验

**检验标准：** 资深工程师 review 时，会觉得这段实现"过度设计"吗？

**适配提示**：空值类型的写法按语言替换（Rust 用 `None`，TS 用 `null`，Go 用零值指针）。

---

## 原则 3：精准修改

> **只动用户要的那行。只清自己造的烂摊子。**

- 不顺手"改进"相邻代码、注释、空白、import 顺序
- 不重构能正常工作的代码——重构应单独立项
- 匹配现有风格，不要按个人偏好改命名/结构
- 看到无关死代码，**标注**而不是**删除**——让用户决定
- 改动产生的孤儿（本次引入的 unused import / var / fn）可以删；预先存在的死代码不要碰

**检验标准：** `git diff` 每一行都能追溯到本次任务吗？

**适配提示**：这条几乎无需改动，是最通用的一条。

---

## 原则 4：目标驱动

> **先写完成判据，再开工。验证到通过为止。**

把模糊指令转成可验证目标：

| 别这样 | 改成这样 |
|---|---|
| "加输入校验" | "为非法输入写测试，让它们通过" |
| "修 bug" | "写一个能复现 bug 的测试，让它通过" |
| "重构 X" | "重构前后跑一遍测试，断言行为不变" |
| "优化 UI" | "明确：哪个组件、哪种屏宽、对照截图/录屏" |

多步骤任务先列出验证点再做：

```
1. [步骤] → 验证：[可执行的检查]
2. [步骤] → 验证：[可执行的检查]
```

**检验标准：** 在动手前，能不能用一句话写出"完成的样子"？

**适配提示**：如项目无测试框架，把"写测试"替换为项目实际的验证手段（手动验证步骤、类型检查、lint）。

## 通用反例对照表（可直接套用）

以下反例跨技术栈通用，初始化时可直接加入 AGENTS.md，再叠加项目特定反例：

| ❌ 不该做 | ✅ 应该做 |
|---|---|
| 改 bug 时顺手重构相邻函数 | 只改最小代码；重构开独立任务 |
| 为单次脚本加抽象 | 直接实现，重复 3 次再抽象 |
| 不可填值兜底用空字符串 / `-1` / `0` | 用空值类型，调用方显式处理 |
| 删除"看似无用"但不理解的代码 | 标注疑似死代码，让用户判断 |
| 为"以后可能要扩展"留 unused 接口 | 不留，需要时再加 |
| 需求不清就默默选一个方案 | 列出选项，请用户选 |
| 改完后才发现一堆编译失败 | 改完立即跑快速验证（typecheck / check） |
| 越界改无关代码、注释、格式 | `git diff` 每行都能追溯到任务 |

## 红线规则设计指南

红线规则是 AGENTS.md 区别于通用指南的核心。**诊断时主动帮项目找红线；初始化时根据项目类型预填**。

### 红线四类来源

按这四类逐一排查，几乎能覆盖所有项目的红线：

#### 来源 1：一致性约束（一处改，多处同步）
**找法**：问"项目里有哪些改动需要同时改多个文件？" 
**典型**：
- 多个 adapter / plugin / provider 需保持接口一致
- 新增命令需同时注册到多处（如 Rust 的 `mod.rs` + `lib.rs`）
- 新增路由 / 页面需更新路由表
- schema 改动需加 migration

**写法示例**：
```markdown
1. **[模块] 一致性**：改 [路径/trait] 后，必须确认 [N 个相关文件] 仍能编译且行为一致。改完立刻跑 `[验证命令]`。
```

#### 来源 2：工作流约束（强制流程）
**找法**：问"项目要求 agent 走什么流程才能改代码？"
**典型**：
- spec 驱动（propose → apply → archive）
- 改动前先写测试
- PR 模板 / code owner 审批

**写法示例**：
```markdown
2. **[工作流名]**：代码改动前先 [propose / 写测试 / 开 issue]（[例外情况] 除外）。
```

#### 来源 3：安全约束（不能自主做的操作）
**找法**：问"哪些操作 agent 绝不能擅自执行？"
**典型**：
- 不主动 `git push` / `git tag`
- 不提交密钥 / `.env`
- 不提交构建产物（`dist/` / 二进制）
- 不部署到生产

**写法示例**：
```markdown
3. **不主动 push / tag / 部署**：未经用户明确指示，禁止 `git push`、`git tag`、提交构建产物。
```

#### 来源 4：硬编码禁令（不能写死的值）
**找法**：问"项目里哪些值必须走配置 / 注册表 / i18n，不能写字面量？"
**典型**：
- i18n 文案（走 `locales/*.json` + `t("key")`）
- 工具 / feature 标识（走 registry / enum）
- magic number（走常量 / config）
- API 端点 / 密钥（走 env）

**写法示例**：
```markdown
4. **[类别] 不硬编码**：[值] 走 [配置位置]。代码内禁止 [字面量写法]。
```

### 红线写法的三个要素

每条红线必须包含：
1. **触发条件**：什么情况下适用（改了什么 / 什么时候）
2. **必做动作**：必须做什么（跑什么命令 / 同步改哪里）
3. **后果**：违反会怎样（必返工 / 编译失败 / 行为不一致）

❌ 口号红线（缺三要素）：
```markdown
- 注意 adapter 一致性
```

✅ 合格红线（三要素齐全）：
```markdown
- **8 个 adapter 一致性**（触发）：改 trait 后（触发），必须确认 8 个 adapter 仍编译且行为一致（动作），否则必返工（后果）。改完立刻跑 `cargo check`（动作）。
```

### 不同项目类型的默认红线

| 项目类型 | 通常需要的红线 |
|---|---|
| **前端 / 全栈** | i18n 不硬编码、不提交构建产物、路由同步 |
| **后端 / API** | schema 改动加 migration、不提交密钥、API 版本兼容 |
| **库 / SDK** | 公共 API 变更需 semver、不破坏向后兼容、changelog 更新 |
| **桌面 / Tauri / Electron** | 命令双注册、schema migration、原生权限声明同步 |
| **monorepo** | 跨包改动的一致性、依赖版本同步 |
| **CLI 工具** | 命令/参数向后兼容、help 文本同步 |

## 项目适配 checklist

初始化时，过一遍这个 checklist 确保项目层信息采集齐全：

- [ ] 项目一句话定位 + 技术栈（写进标题区）
- [ ] 项目类型判定（小/中/大 → 决定章节取舍，见 `anatomy.md`）
- [ ] 实际可跑的命令（dev / build / test / lint / typecheck）—— 查 `package.json` / `Makefile` / `Cargo.toml`
- [ ] 项目"不看就会错"的 gotchas（问维护者 / 查 README / 查架构）
- [ ] 四类红线（一致性 / 工作流 / 安全 / 硬编码）逐一排查
- [ ] 提交规范（查 `git log` 看实际风格）
- [ ] 文档结构（查 `docs/` 实际目录）
- [ ] 是否有 CLAUDE.md / `.cursorrules` / `GEMINI.md` 等需收敛的规则文件

**信息不足时的处理**：宁可留 `<!-- TODO: 待补充 -->` 占位让用户填，也不要臆测。臆测出的命令和路径会成为"文档腐烂"的源头。
