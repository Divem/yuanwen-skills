# 写作规则

10 条核心写作规则 + 配置维度 + 追加到 CHANGELOG.md 的规则。第 5 步（提炼）和第 6 步（生成/追加）时读。

> 这些规则来自对 20 款产品 changelog 的共性提炼。理解每条的**原因**，比死记格式重要——格式是结果，原因是源头。

## 十条核心规则

### 1. 利益先行

先说用户能得到什么，再说技术细节。用户关心"这对我有什么用"，不关心你重构了什么。

- ✅ "切换标签页快了 3 倍"
- ❌ "重构了路由状态管理，引入了虚拟列表"

### 2. 展示优于讲述

能配截图/GIF 就不纯文字；能用具体路径就不抽象描述。视觉比文字更易理解、更有感染力。

- ✅ `![暗色模式](assets/dark-mode.png)` + 一句话
- ❌ 三段文字描述暗色模式长什么样

> 没有素材时，留占位符 `![描述](待补充)`，提醒用户后续补图，不要硬编造。

### 3. 每条回答 "So What"

写完每条，自问"用户读完知道这对自己意味着什么吗？"如果只是技术陈述，翻译成用户价值，或删掉。

- ✅ "搜索支持中文模糊匹配了——记不清全名也能搜到"
- ❌ "搜索索引新增了 n-gram 分词"

### 4. 一致性优先

同一项目的所有条目遵循同一套结构：同样的分类标签、同样的日期格式、同样的标题层级。一致性比单条写得漂亮更重要——它是专业感的来源。

选定了风格（如 Raycast 的 ✨💎🐞），后续每次都用这套，别这次 Emoji 下次又换成 Added/Improved/Fixed。

### 5. UI 路径代码化

菜单、设置、按钮、命令名用内联代码（反引号），路径用 `→` 连接。让用户一眼知道去哪点。

- ✅ `Settings → Appearance → Theme`
- ❌ "在设置里的外观主题选项"

### 6. 功能名加粗

列表项以 `**功能名**：描述` 呈现，方便用户快速扫读定位关心的功能。

- ✅ `- **全局搜索**：速度提升约 3 倍`
- ❌ `- 全局搜索速度提升了`

### 7. Breaking change 显式标记

破坏性变更必须突出（`⚠️` 或独立小节），并附**迁移指引**。这是对用户负责——升级前他们需要知道会不会出问题。

```markdown
#### ⚠️ Breaking
- **API**：字段 `userId` 重命名为 `user_id`。迁移：批量替换请求体字段名，旧字段将在 v2.6.0 移除。[迁移指南 →](docs/migration)
```

### 8. 链接到行动

不只链接到文档（被动阅读），还链接到"Try it now"、"去试试 →"等操作入口（主动引导）。降低用户使用的摩擦。

- ✅ `[去试试暗色模式 →](settings/appearance)`
- ❌ `[暗色模式文档](docs/appearance)`

### 9. 反馈闭环（可选但加分）

如果某功能是基于用户/社区反馈做的，标注出来（"基于大家反馈"、"你问得最多的"）。这证明反馈被重视，建立信任。

- ✅ "你们在论坛提得最多的暗色模式，来了。"
- ⚠️ 没有真实反馈来源时不要编造。

### 10. 避免夸大

不用"革命性"、"颠覆性"、"game-changing"等无法验证的词。用具体的、可感知的描述。夸大反而损害可信度。

- ✅ "快了约 3 倍"
- ❌ "性能实现了革命性飞跃"

## 配置维度参考

生成时若用户有特殊要求，可按这些维度调整（默认值见 SKILL.md 的"配置"）：

| 维度 | 可选项 | 默认 |
|------|--------|------|
| 日期格式 | `YYYY-MM-DD` / `July 2, 2026` / `2026年7月` / `Jul 2026` | `YYYY-MM-DD` |
| 版本标识 | semver(`v1.2.0`) / 日期 / 无 | 日期；有 git tag 时用 semver |
| 分类标签 | Emoji(`✨💎🐞`) / 文字(`Added/Improved/Fixed`) / `[产品域]` 前缀 / 无 | 跟随所选风格 |
| 条目长度 | 极简(一句话) / 简短(一段) / 中等(段+列表) / 长叙述(多段) | 跟随所选风格 |
| 语气 | 技术化 / 对话式 / 正式 | 跟随所选风格 |
| UI 标注 | 内联代码 / 加粗 / 斜体 | 内联代码 |
| 媒体 | 截图 / GIF / 视频 / 无 | 可选截图（留占位符） |
| 作者署名 | 标注 / 不标注 | 不标注（除非 GitHub 风格） |
| 反馈闭环 | 标注来源 / 不标注 | 有真实来源时标注 |

## 追加到 CHANGELOG.md 的规则

### 情况一：文件不存在

用 `assets/changelog-skeleton.md` 创建骨架，把本次条目放在 `## [Unreleased]` 下方（或作为第一个正式版本条目）。

### 情况二：文件已存在

1. **只插入，不改动**：在顶部标题（通常是 `# Changelog` 或 `# 更新日志`）之后、第一条已有条目之前，插入新条目。原有内容一字不动。
2. **倒序**：新的永远在顶部。这是所有产品的共识。
3. **版本/日期去重**：
   - 若新条目与顶部已有条目**同一天/同版本**：询问用户是合并到那条，还是作为新条目。默认建议合并（同一天的更新分开写显得碎）。
   - 若是不同版本：直接插入。
4. **格式对齐**：观察文件已有的日期格式、标题层级、分类风格，**尽量对齐已有风格**——除非用户明确要换风格。一致性 > 个人偏好。
5. **写入前确认**：把将要插入的完整内容（含上下文几行）展示给用户，确认后再写文件。

### 插入示例

原有：

```markdown
# Changelog

## [v1.2.0] — 2026-07-12
### ✨ New
- 旧功能...
```

追加后：

```markdown
# Changelog

## [v1.3.0] — 2026-07-19          ← 新插入
### ✨ New
- 新功能...

## [v1.2.0] — 2026-07-12          ← 原有，下移
### ✨ New
- 旧功能...
```

## 常见反模式

写完自查，避免这些：

| 反模式 | 问题 | 修正 |
|--------|------|------|
| 抄 commit message | 技术视角，用户看不懂 | 翻译成用户价值 |
| 堆砌技术细节 | "重构了 X、优化了 Y" | 只保留用户能感知的 |
| 空洞形容词 | "大幅提升"、"全新体验" | 给具体数字或场景 |
| 漏掉 Breaking | 用户升级踩坑 | 必须突出 + 迁移指引 |
| 一条更新写五段 | 信息过载 | 精简到核心利益点 |
| 编造截图链接 | 点击 404 | 留占位符或省略 |
| 顺序混乱 | 新旧夹杂 | 严格倒序，分类内部也按重要性排 |
| 中英文混用不一致 | 一会儿"修复"一会儿"Fix" | 全文统一（跟随项目语言） |

最后一条尤其重要：选定语言后，标题、分类、描述全文统一，不要中英混杂。
